# 运维配置审计方法论

## 什么时候做配置审计

1. **接手新环境**：快速发现历史遗留问题
2. **每次发布前**：确认配置变更不会影响线上
3. **定期巡检**：每周/每月做一次配置一致性检查
4. **故障复盘后**：检查同类配置是否在其他环境也存在

## 审计原则

- **只读**：不修改任何配置
- **最小权限**：只需要读取权限
- **可重复**：同一批输入反复执行应得到一致结果
- **可解释**：每个发现都要有明确的问题描述和修复建议

## 风险等级定义

| 等级 | 含义 | 处理建议 |
|------|------|---------|
| 🔴 高 | 可能导致服务不可用或安全风险 | 立即修复 |
| 🟡 中 | 可能导致配置不一致或运维隐患 | 计划修复 |
| 🟢 低 | 建议优化，但暂不紧急 | 观察 |

## 常见配置风险

### Nginx
- proxy_pass 指向不存在的 upstream
- upstream 已定义但没有 server 引用（死代码）
- server_name 和证书域名不匹配

### SSL 证书
- 证书过期
- 证书 SAN 未覆盖服务域名
- 证书和私钥不匹配

### K8s
- ConfigMap 改了但 Deployment 没重启
- Secret 缺失或键值不对
- Ingress TLS secret 不存在
- 不同环境配置漂移
