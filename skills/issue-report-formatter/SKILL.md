# Issue Report Formatter · 运维问题上报格式化器

## Overview

把"东一句西一句"的故障描述，快速整理成结构化、可直接复制到企业微信/钉钉/邮件的标准化运维问题上报报告。

**解决什么痛点**：运维/技术支持人员遇到问题时，经常手忙脚乱地组织上报格式——客户名是什么、哪个环境、哪个节点、完整报错日志、已经试过什么操作、复现步骤……每次手动拼凑，既慢又容易漏字段，导致接手人需要反复追问。

**核心能力**：
1. **对话式输入**：用户自然语言描述故障 → 自动抽取关键字段 → 生成结构化报告
2. **表单式输入**：用户逐字段提供 → 格式化输出
3. **紧急度分级**：根据影响范围/客户级别自动标注 🔴紧急 / 🟡重要 / 🟢普通
4. **建议下一步**：基于报错特征给出初步排查方向（不替代人工判断）
5. **AI 协作模式（assist）**：格式化报告后，自动生成结构化提示词 + 排查 checklist + 诊断假设树，用户复制粘贴给任意 AI 即可辅助排查

**适用场景**：
- 运维工程师向 leader/同事上报生产故障
- 技术支持向研发团队转交客户问题
- 私有化交付过程中向原厂报障
- SRE 团队内部故障交接
- **整理故障信息同步给 AI（ChatGPT/Claude/WorkBuddy 等），让 AI 辅助排查根因**（assist 模式）
- 任何需要"把模糊问题描述清楚"的技术沟通场景

**不适用场景**：
- 自动诊断根因（本 Skill 只做格式化，不做诊断）
- 自动执行修复操作（只生成报告，不碰生产环境）
- 替代正式的工单系统（本 Skill 是"格式化器"，不是工单系统）

## 工作流程

### 触发方式

用户说以下任一短语时触发：
- 中文：问题上报 / 故障上报 / 报障 / 上报问题 / 整理报错 / 格式化故障报告
- 英文：issue report / bug report format / incident report

### 对话使用示例（用户怎么用）

**你不需要去终端敲命令。** 装了这个 Skill 后，直接在对话里描述故障，WorkBuddy 会自动识别触发短语并加载本 Skill。

#### 场景 1 · 生产故障上报（最常用）

碰到问题时，直接把零散的描述丢给对话：

> **你说**：帮我做个问题上报。prod-server 上 app-service 8090 的 /api/health 返回 502 service_unavailable，已经重启过 core 服务 8080 但没解决

Skill 自动抽取关键字段（客户名/环境/报错/已试操作），生成结构化上报报告 + 紧急度分级，可直接复制到企业微信/钉钉发给 leader 或同事。

#### 场景 2 · 整理给 AI 辅助排查（assist 模式）

> **你说**：整理给 AI 排查 / 同步给 AI 帮我查

在标准报告之外，额外生成三份 AI 协作产物：结构化提示词 + 排查 checklist + 诊断假设树。你把提示词复制粘贴给任意 AI（ChatGPT/Claude/WorkBuddy），AI 按假设树逐个验证给诊断命令，你跑命令把输出贴回给 AI，AI 解读给根因和修复方案。

#### 场景 3 · 客户报障转交研发

> **你说**：报障。客户A，生产环境 10.0.1.5，报错推理服务 500，已试过重启 minio

生成标准报告，附客户名/环境/报错/已试操作，转交给研发时信息完整不用反复追问。

#### 场景 4 · 逐字段表单式上报

> **你说**：问题上报。客户名：客户A；环境：生产；节点：10.0.1.5；报错：推理服务 500；已试操作：重启 minio

逐字段提供，直接格式化输出，缺失字段标记 `[待补充]`。

### 执行步骤

#### Step 1 · 判断输入模式

读取用户输入，判断是"对话式""表单式"还是"AI 协作式"：
- **对话式**：用户用自然语言描述了一段故障（如"prod-server 上 app-service 8090 的 /api/health 返回 502 service_unavailable"）→ 走 Step 2A
- **表单式**：用户明确逐字段提供（如"客户名：客户A，环境：生产，节点：10.0.1.5..."）→ 走 Step 2B
- **AI 协作式**：用户说"整理给 AI 排查""同步给 AI""让 AI 帮我查"等 → 走 Step 2A + Step 6
- **模糊**：用户只说"帮我做个问题上报"但没给详情 → 主动询问关键字段

#### Step 2A · 对话式抽取（自然语言 → 结构化）

调用 `scripts/format_report.py --mode extract`，从自然语言中抽取以下字段：

| 字段 | 抽取规则 | 示例 |
|------|---------|------|
| 客户名 | 匹配"客户XX""XX项目""为XX"或已知客户名 | 客户A |
| 环境/节点 | 匹配 IP/主机名/namespace/服务名 | 10.0.1.5 / prod-server / production |
| 完整报错 | 匹配"返回XX""报错XX""失败""不可用"及紧跟的日志 | 502 service_unavailable |
| 已试操作 | 匹配"已试过""重启过""检查了"及紧跟的动作 | 重启 core 服务 |
| 复现步骤 | 匹配"复现""触发""步骤"或按时间线整理 | curl /api/health → 502 |

抽取不全的字段，标记为 `[待补充]`，不臆造。

#### Step 2B · 表单式格式化（逐字段 → 标准格式）

调用 `scripts/format_report.py --mode format`，把用户提供的字段直接填入模板，缺失字段标记 `[待补充]`。

#### Step 3 · 紧急度分级

调用 `scripts/classify_severity.py`，根据以下规则自动分级：

| 级别 | 触发条件 | 标记 |
|------|---------|------|
| 🔴 紧急 | 生产环境 + 核心服务不可用（502/503/超时/宕机） | urgent |
| 🟡 重要 | 生产环境 + 部分功能异常，或非生产环境核心服务不可用 | important |
| 🟢 普通 | 非生产环境 + 部分功能异常，或仅为咨询/优化建议 | normal |

**安全边界**：分级只是建议，最终以人工判断为准。脚本会在分级后标注"（自动分级，请人工复核）"。

#### Step 4 · 生成报告

输出两份：

**① Markdown 报告**（主输出，可直接复制）：
```markdown
## 问题上报

- **客户名**：客户A
- **环境/节点**：生产 / 10.0.1.5 / production
- **完整报错**：app-service 8090 的 /api/health 返回 502 service_unavailable
- **已试操作**：重启 core 服务（8080），问题未解决
- **复现步骤**：
  1. curl http://10.0.1.5:8090/api/health
  2. 返回 {"code":502,"msg":"service_unavailable"}
- **紧急度**：🔴 紧急（自动分级，请人工复核）
- **建议下一步**：
  - 检查 core 服务 8080 是否真的起来（netstat/ss）
  - 检查 app-service 到 core 的网络连通性
  - 查看 core 服务日志最近报错
```

**② JSON 结构化数据**（便于批量统计/知识库沉淀）：
```json
{
  "customer": "客户A",
  "environment": "生产 / 10.0.1.5 / production",
  "error": "app-service 8090 /api/health 502 service_unavailable",
  "tried": "重启 core 服务 8080",
  "reproduce": "curl http://10.0.1.5:8090/api/health → 502",
  "severity": "urgent",
  "suggestions": ["检查 core 8080 端口", "检查网络连通性", "查看 core 日志"],
  "timestamp": "2026-10-31T13:30:00+08:00"
}
```

#### Step 5 · 变现引导（可选，默认开启）

报告末尾自动附加（可在 config 里关闭）：

```
---
💡 需要专业运维支持？这个故障的根因排查/代维服务可联系：[你的联系方式]
📚 更多运维实战内容 → 公众号：[你的公众号名]
```

#### Step 6 · AI 协作模式（assist，可选）

如果用户希望"整理给 AI 辅助排查"，调用 `scripts/format_report.py --mode assist` 或 `scripts/generate_ai_prompt.py`，在标准报告之后额外输出三份 AI 协作产物：

**① 结构化提示词**（可直接复制粘贴给 ChatGPT/Claude/WorkBuddy 等任意 AI）：
- 内含完整故障上报信息 + 排查要求 + 安全约束
- 要求 AI 按"先列假设 → 跑诊断命令 → 解读结论 → 给修复方案"流程推进
- 每一步等用户确认后再做下一步，避免一上来就"重启试试"

**② 排查 Checklist**（用户也可自己照着查）：
- 基于报错类型（502/503/timeout/connection refused/404/401 等）自动匹配
- 每项含"检查什么 + 怎么查 + 具体命令"
- 附带用户已试操作，避免 AI 重复建议

**③ 诊断假设树**（给 AI 的思考框架）：
- 列出 top 4 可能原因 + 每个的验证方法 + 预期结果
- 引导 AI 按顺序逐个验证，验证完一个再下一个，不跳步

**使用流程**：
```
用户描述故障
    ↓
Skill 生成标准报告 + AI 协作产物
    ↓
用户复制【产物 1 提示词】粘贴给任意 AI
    ↓
AI 按假设树逐个验证，给诊断命令
    ↓
用户跑命令，把输出贴回给 AI
    ↓
AI 解读 → 给根因 + 修复方案
```

**安全边界**：assist 模式只生成提示词，**不直接调 AI API**（避免密钥管理复杂度和成本），用户自己复制粘贴给 AI。

## 约束与边界

### 安全红线
1. **不臆造字段**：抽取不到的字段标记 `[待补充]`，绝不编造客户名/环境/报错内容
2. **不执行诊断**：本 Skill 只做格式化，不做根因诊断（"建议下一步"和"诊断假设树"是启发式提示，不是诊断结论）
3. **不碰生产环境**：只生成报告和提示词，不执行任何命令、不调用任何 API、不修改任何配置
4. **assist 模式不直接调 AI API**：只生成提示词让用户复制粘贴，避免密钥管理和成本问题
5. **敏感信息脱敏**：报告中的 IP/密码/token 默认保留（用于内部上报），但导出到外部时会提示"请确认是否需要脱敏"

### 变现接口
- 报告末尾的代维服务引导和公众号引流默认开启
- 用户可在对话中说"不要加引导"或"关闭变现"来关闭
- 变现引导只加在 Markdown 报告末尾，不加在 JSON 里（保证数据干净）

### 适用边界
- 适合：运维/技术支持/SRE 场景的结构化上报
- 不适合：替代正式工单系统、自动诊断根因、自动修复故障
